## Context

A patch is the synth alone. Everything else that makes a part sound the way
it does is the song's: the insert chain on its strip, the strip's low cut,
and the sequencer that plays it. tacowars wants to bundle a sound generator
with the devices around it, save that bundle under a name, browse the bundles
and drop one onto a part. Windsor has no users yet and no legacy to protect,
so the design is free to take the clean shape.

What the engine and the console hold, read from the code on 2026-10-17:

- **A part already is a rack.** `DocumentPart` carries the slot, the name,
  the colour, `preset` (an id into the song's `patches`), `patchSource`,
  `velocity`, `regions`, `sequencer`, `strip` (output, mute, solo, level,
  pan, `lowCut`, `sends`, `inserts`), `automation` and `ccMappings`. The
  Song tab draws it as a device row: the sequencer device, then the patch,
  then the insert rack. The song carries all of it by value (invariant 3).
- **The library is files in IndexedDB.** A patch is one file's text under
  its id in the `patches` store, read through the one loader
  (`loadPatchFile`). Save, Save as…, Revert and the modified dot work from
  `patchSource`, the part's link back to the library entry, which nothing
  that plays reads and `system/patchSourcePartial.ts` strips from a live
  partial. Built-ins are read-only and Save forks them.
- **The chain is self-describing.** `normaliseInserts` reads any chain
  against the insert registry: defaults filled, numbers clamped, unknown
  kinds dangling, each insert carrying a stable id unique within its chain.
  Lanes and CC mappings address an insert by that id.
- **A sequencer config is its pattern.** `normaliseSequencer` reads any
  `SequencerSpec` by kind; the `seed` is the part's, and a region may hold a
  pattern of the part's kind only.
- **Two things name the song, not the sound.** A compressor's or a Pump's
  external key is `{ track: slot }`, another part's slot. Automation lanes
  and CC mappings sit in song time and on a controller.

## Decisions

### What a rack is

1. **A rack is a library object, never a song object.** It is a part's
   sound with the song-specific state left out, saved under its own id,
   and expanded into a part when loaded. The song document gains no rack
   section: a loaded rack is the part's own patch, chain and sequencer, as
   today, so invariant 3 holds unchanged. Two parts loaded from one rack
   share nothing, as two parts loaded from one patch share nothing.
2. **The members.** A rack holds:

   | Member | Required | Notes |
   |---|---|---|
   | `patch` | yes | a `Patch` by value, as the song's `patches` entry holds it |
   | `patchSource` | no | the library patch id the patch came from; provenance only |
   | `inserts` | yes, may be empty | the strip's chain, every spec with its wet-path child and its insert id |
   | `lowCut` | no | the strip's low cut in Hz; absent leaves the loaded part's |
   | `sequencer` | no | the whole `SequencerSpec` without `seed`; absent leaves the loaded part's |
   | `name`, `category`, `tags`, `description` | yes | the same four fields as a patch file |

   Level, pan, sends, output, mute, solo, regions, automation lanes, CC
   mappings, the colour and the part's name stay in the song. The
   sequencer and the low cut are optional because a drum sound wants its
   pattern and its cut as often as not, and a pad wants neither (tacowars,
   2026-10-17).
3. **An external sidechain key is cleared on save.** A compressor or Pump
   keyed from `{ track: slot }` is written as `{ track: null }`, explicitly
   disconnected, since the slot means nothing outside the song. `internal`
   is kept. The browser's info pane says so, and the user re-picks the key
   after a load.
4. **Insert ids travel with the rack.** They are kept as saved and checked
   unique within the chain on load, as `chainIds` already does. A loaded
   chain therefore reads back with the same ids on every load, so an undo
   that brings a rack's chain back brings its lanes back with it.
5. **Rack macros are not in this change.** A patch's own macros ride inside
   its patch. A part-level macro that also reaches an insert's fields is a
   later feature, useful on any part, and the target vocabulary for it
   already exists in the automation catalog. Kits (one object that loads
   several parts) and parallel chains are out of scope too.

### The file

6. **One file per rack.** A rack file is

       { "format": 1, "kind": "rack", "name", "category", "tags": [],
         "description", "patchFormat": 4, "patch": { … }, "patchSource"?,
         "lowCut"?, "sequencer"?: { "kind", … }, "inserts": [ … ] }

   `kind: "rack"` tells it from a patch file, which carries no `kind`; a
   file without one is a patch. The id is the file name's slug, under
   `PATCH_ID_RULE`, immutable; `name` is the display name and equals
   `patch.name`. `patchFormat` is the embedded patch's own format, so the
   patch is upgraded through the patch table as a song's snapshot is and
   the two format counters never have to move together (settled while
   building issue A).
7. **`RACK_FILE_FORMAT` starts at 1 and follows the format rules.** A file
   whose `format` or `patchFormat` this build cannot read is refused with
   its text kept, never loaded wrong (`2026-09-28-format-versions-refuse-never-destroy`). The
   patch section is checked by the patch loader's own rules: a missing key
   fills from `makePatch()`, an unknown key or a wrong-typed leaf refuses
   the file. The chain and the sequencer are read by the engine's
   normalisers with a reporting `FieldNormaliser`: a missing field fills
   from the kind's defaults, a number out of range is clamped and the
   clamp is a load problem, and an insert kind or a sequencer kind this
   build lacks refuses the file. A `seed` inside the sequencer is dropped
   silently, as `normaliseSequencer` already does for a region's pattern.
8. **The engine owns the contract.** `rack/rackFile.ts` (the type, the
   loader, the serialiser) and `rack/rackConstants.ts` beside `patch/`,
   exported from the index. The serialiser writes the same bytes as a
   download, as `serialisePatchFile` does, so a stored record, a download
   and a folder file are one format.

### The song

9. **`rackSource` on the part, and nothing else.** `DocumentPart` gains an
   optional `rackSource?: string`: the library rack id the part was loaded
   from, with the rules of `patchSource`: a non-empty string is kept, a
   junk value is dropped with a report, nothing that plays reads it, and
   `AudioSystem.apply` strips it from a live partial through the same seam
   as `patchSource` (`withoutPatchSource` becomes the strip of both
   links). It is additive, so `ARRANGEMENT_VERSION` does not change. It
   is cleared when the part's patch is replaced by a patch load, Init or
   Save as…, and kept through a knob edit, an insert edit and a rename.

### Loading a rack into a part

10. **One change, one undo step.** Loading rack `R` into slot `S`:
    - the patch goes into `patches` under `uniqueId(R, taken)`, where
      `taken` is every library id and every song patch id; `S.preset`
      names it, `S.patchSource` is `R.patchSource` when that names a
      library patch and is absent otherwise, and `S.rackSource` is `R`;
    - `S.strip.inserts` is replaced by `R.inserts`;
    - `S.strip.lowCut` is set when `R` carries one;
    - `S.sequencer` is replaced when `R` carries one. The seed is the
      part's, never the rack's: a part of the same kind keeps its own, and
      a part of another kind gets a new part's (`freshSequencer`). The
      regions are treated as a kind change is today (`setSequencerKind`):
      a region pattern of another kind is dropped, a Roll's ∞ region is
      fitted, and a same-kind load leaves them alone (settled while
      building issue B);
    - every lane and CC mapping on an insert id the new chain lacks is
      removed in the same partial, so the normaliser reports nothing and
      one undo brings the lot back;
    - the part's old patch leaves the song by the existing rule
      (`leftCopyDrop`), an unedited automatic copy only.
11. **The discard guard.** When the part's patch or chain differs from its
    sources (the patch's modified rule, and decision 14's rack rule), the
    load asks first, with the confirm dialog Load already uses.
12. **Add part from rack** is `addPartChange` followed by decision 10 on
    the new slot, as one change.

### Saving a rack

13. **Save as rack…** builds the rack from the part (decisions 2 and 3),
    opens the metadata modal with the name prefilled from the patch's
    name, the category and tags from the patch's library entry when it has
    one, and two checkboxes. The name is the rack's and, by decision 6, the
    embedded patch's: the file writes it into its patch copy, so a part
    loaded from the rack plays a patch of the rack's name, and the library
    patch the rack came from keeps its own (settled while building issue
    B). The two checkboxes are **Include low cut**, checked when the part's
    low cut is above the floor, and **Include sequencer**, checked when the
    part's kind is not `none`. It writes into the user library under
    `uniqueId(slug(name), taken)` and sets the part's `rackSource`. The
    user-visible text is US English.
14. **Save rack, Revert rack and the rack's modified dot** follow the
    patch's rules over `rackSource`: the dot compares the part's patch
    leaves, chain, low cut and sequencer (less seed) against the library
    rack, member by member, a member the rack lacks never counting, the
    patch's `name` left out, and the chain compared with its external
    sidechain keys cleared as the file writes them (decision 3), so a part
    keyed from another part is clean against the rack it was saved from
    and the key stays the song's. The patch's own dot (`isModified`) leaves the
    name out too, everywhere: a name is metadata Save writes anyway, so a
    dot means a sound edit, a renamed song copy shows none, and neither dot
    is lit right after a rack load (whose patch takes the rack's name,
    decision 6) or a Save as rack… under a new name (which writes that name
    into the rack's patch and leaves the song patch's). Settled by tacowars
    on the mockup (windsor#876), built by issue D; Save
    rack writes over a user rack and forks a built-in to a new id, as Save
    does for a patch; Revert rack loads the library rack again by decision
    10 without the confirm. The patch's own dot, Save and Revert keep their
    meaning over `patchSource`, so a rack-loaded part has two levels of
    save, the patch's and the rack's, as it has two levels of library
    object.

### Storage, built-ins and the folder grant

15. **IndexedDB.** The `windsor` database goes to version 3 with a `racks`
    object store, key the rack id, value the file's text, additive as
    version 2 was. The store is a `PatchFolder` (`list`, `read`, `write`,
    `remove`) under a second name, so the model, the actions and the tests
    reuse the folder abstraction and its in-memory fakes unchanged.
    `LibraryModel` gains the rack entries and their writable ids beside
    the patch ones.
16. **Built-in racks are files.** `packages/engine/src/racks/<id>.json`,
    one per rack, with `scripts/patch-library-index.mjs` generalised to a
    second folder and a generated `racks/index.ts`, checked by `verify` as
    the patch index is, and loaded as its own chunk as the patch bank is.
    The developer's File System Access grant writes racks into that folder
    while connected, so a user rack is promoted to a built-in the way a
    patch is. The first bank is tacowars's, by ear.
17. **Export.** A rack row's Export downloads `<id>.json`. Importing a
    file into the library is a follow-up shared with patches, which have no
    import of their own today either; the folder grant and the script
    cover authoring until then.

### The console

18. **One browser.** The full-pane patch browser gains a **Kind** facet,
    Patches | Racks, ahead of category, tags and source, which are shared.
    A rack row shows its name, category and a short chain line
    (`Reverb → Compressor`, the kinds' labels in order) and a pattern mark
    when it carries a sequencer. The info pane adds the patch's name and
    library origin, the chain with each insert's enabled state, the
    sequencer kind, the low cut, and a disconnected key where decision 3
    applies. Load into runs decision 10. The browser is `reviewed` UI, so
    its rack rows and pane are mocked first (`docs/design/`), from a
    screenshot of today's browser with real values.
19. **Entry points.** The patch bar's ⋯ menu gains **Save as rack…**,
    **Save rack** and **Revert rack**, the last two only while the part has
    a `rackSource`; while it has one, the patch box shows a **RACK** tag
    carrying the rack's dot (decision 14) before the patch's name, on the
    one line the box has today, and the tag's title names the rack. The
    patch's name is the rack's right after a load (decision 6), so one name
    serves both, and a renamed song copy keeps its own name beside the tag.
    (Settled by tacowars on the mockup, windsor#876: a second line made the
    bar taller, a box of its own cost its width.) The Song tab's row context
    menu gains **Load rack…**, which opens the browser on Racks with that
    part as the target, and the parts list's add gains **Add part from
    rack…** (decision 12): a click on + adds a part as today, and a
    right-click or a long press on it opens a two-row menu, Add part and
    Add part from rack… (settled there too).
20. **Naming.** The library object is a **Rack** in every label. The code's
    "insert rack" keeps its name for the row of inserts; a doc that means
    the library object says "a saved rack" where the two could be read as
    one.
